# atry AI 基座设计包 · 00 总览与设计原则

> 状态：设计草案（2026-11-19），评审中；本设计包只描述**问题、模型、契约、取舍与验收**，不包含实现代码。
> 读者：项目 owner、后续参与的 agent、面试复盘。

## 1. atry 是什么（与 btry 的关系）

- **btry**：通用业务基座，历史中包含过垂直业务（网课）内容。即使工作区已清理，其仓库历史/旧文档仍可能让后续 agent 误判项目性质。
- **atry**：与 btry 平级的新基座。工程约定、模块风格、技术栈与 btry 一致，但**从第一天就与垂直业务完全无关**；AI 时代需要的新通用能力在这里沉淀。
- 当前磁盘状态：`atry/` 下有 `btry/`（基座代码）与本设计文档 `docs/design/`；`ltry`（上一轮误创建的垂直产品）已移出到 `blrs/_archive/ltry`，不再出现在 atry。
- **注意**：工作区已干净，但 `atry/btry/.git` 仍是旧仓库（历史含旧业务提交）；严格意义的"干净历史"需要执行 D1（新建独立 atry 仓），见 §7。
- **AI 能力不是垂直业务**。LLM 客服、RAG、内容生成只是使用场景；atry 要做的是这些场景共同依赖的**框架级能力**：调用治理、可靠性、可观测、计量计费、成本控制。

## 2. 设计目标

1. 任何业务（哪怕只是"智能客服"）接入 LLM 时，默认获得生产级保障：并发安全、限流/配额、超时/重试、熔断降级、流式、幂等、可观测、成本可计量。
2. 计量计费是**通用能力**：抽象为 metric/quantity/unit/price 的通用模型，token 只是其中一种计量单位，和 RBAC、支付同为基座模块。
3. 每个模块业务无关、契约先行、可独立测试、可被门禁约束（ArchUnit + Modulith + 数据边界 + 内核纯洁性）。
4. 面试级证据：每个关键设计都有可测量的验证方案（压测、故障注入、对账、SLO），不靠"我觉得"。

### 2.1 核心用例（功能边界）

| 用例 | 触发方 | 期望结果 |
|---|---|---|
| UC-1 同步 LLM 调用 | 业务模块 | 统一响应 + usage + requestId；失败可分类、可重试/降级 |
| UC-2 流式 LLM 调用 | 业务模块/前端 | SSE 流式输出；首 token/chunk 超时、断连取消、部分用量结算 |
| UC-3 额度准入 | 业务模块 | 调用前预扣/配额检查；余额不足 402；并发不超卖 |
| UC-4 用量入账与计价 | 事件/框架 | 事件幂等入账、按价格版本计价、可重算、可对账 |
| UC-5 余额与账单查询 | 业务/运营 | 余额、用量、账单可查；账实一致 |
| UC-6 运营配置 | 运营/开发 | provider/deployment/路由/价格/额度配置可管理、可审计 |
| UC-7 观测与排障 | 运维/agent | 按 requestId/traceId 还原调用、重试、计费与错误 |
| UC-8 对账与补偿 | 运维/财务 | 定期对账、差异可检出、异常预扣可回收 |

## 3. 非目标（明确不做）

- 不做 API 中转站/SaaS 计费产品/充值商城/发票系统；不做多模态生成、RAG 知识库、Agent 编排等垂直能力。
- 不在本期引入独立微服务、Kafka/RocketMQ；先以**模块化单体 + 本地事务 + outbox + 对账**实现，保留演进接口（与 btry《生产级目标架构蓝图》的方向一致）。
- 不追求 provider 全量覆盖；先定义 SPI，用 1 个 mock provider + 1 个真实 provider 验证可扩展性。
- 不做模型训练/推理部署；只做调用侧工程。

## 4. 设计原则

| 原则 | 含义 | 落地约束 |
|---|---|---|
| 业务无关 | 模块内不得出现任何垂直业务词汇/概念 | KernelPurityTest + code review；metering 只认 metric/quantity/price |
| 契约先行 | 跨模块只依赖 `contracts` 中的接口/DTO/事件 | Modulith `allowedDependencies`；ArchUnit 禁止直连实现 |
| 事实源唯一 | 用量事件、账本流水不可变，余额/账单为派生视图 | 事件 append-only；余额由流水/聚合校验；禁止直接改余额 |
| 先准入后账务 | 实时准入（额度/预扣）与账务（rating/账单/对账）分离 | 准入走短事务/内存预扣，账务异步可重放 |
| 失败可分类 | 所有上游/内部错误有稳定分类，决定重试、计费、告警 | 错误 taxonomy + `retryable/billable` 标志 |
| 可观测优先 | 没有 trace/metric/log 字段的调用不允许上线 | 统一 event schema + OTel GenAI 映射 + SLO |
| 默认安全 | 日志默认不落 prompt/response；密钥不落日志/DB 明文 | 脱敏规则、API Key 只存哈希、敏感字段白名单 |
| 可回退 | 每个优化都有开关/基线；策略可配置 | feature flag + 压测报告 + 回滚预案 |
| 渐进演进 | 先模块化单体，后按证据拆分 | 契约/事件边界先立，部署形态后变 |

## 5. 质量属性与验收标准（总）

| 质量属性 | 目标（待压测校准） | 验证方式 |
|---|---|---|
| 并发/吞吐 | mock provider 下 ≥ 1,000 req/s（4C8G 单机，p99 ≤ 200ms）；真实 provider 受上游配额约束 | wrk/k6 分档压测 + 与基线对照 |
| 延迟 | 网关自身开销 p99 < 15ms（不含上游）；TTFT 分解可观测 | 微基准 + trace 拆解 |
| 可靠性 | 429/超时/5xx 按策略处理；无重试风暴；单 provider 故障不影响全局 | 故障注入矩阵 |
| 计量一致性 | 事件数=计量数=计费数；账实差异=0（容差内） | 对账任务 + 不变量测试 |
| 结算延迟 | 异步结算 p99 < 2s（可配置），停机可恢复 | 压测 + 崩溃恢复测试 |
| 可观测 | 每次调用可按 request_id/trace_id 还原完整链路与费用 | trace/log 字段验收 |
| 安全 | prompt/response 默认不落日志；密钥零明文 | 日志扫描测试 + code review |
| 可测试 | 模块测试不依赖真实 provider；集成测试可本地一键跑 | CI 门禁 |
