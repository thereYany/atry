## 2. 调研结论 A：限流与并发

1. **限流维度不能只有 RPM**：至少 RPM、TPM（输入+输出）、并发在途、日配额/预算。长上下文场景 TPM 才是真瓶颈；部分 provider（如 Azure，据其配额文档）按 1s/10s 小窗口评估，且被拒请求可能计入速率——客户端必须发送端平滑，不能"打了再重试"。（该细节为文档摘要，未逐条复验）
2. **算法分层**：令牌桶/GCRA 适合入口（允许可控突发、O(1)）；滑动窗口日志（ZSET+Lua）精确但 O(N)；漏桶平滑；并发用信号量。Stripe 用四种限流器叠加（per-account 令牌桶、并发上限、fleet/worker load shedder），说明单一算法覆盖不了多目标。
3. **Redis 限流**：Lua 原子、脚本短小、常驻 `EVALSHA`、key 走 KEYS、用 Redis 服务端时间；限流器故障不能 fail-closed 打挂全站，需要本地兜底（与 btry Redis 降级策略一致）。
4. **429 要当指令**：读 `Retry-After`/`retry-after-ms`；区分限流、配额耗尽、服务过载（可重试）与 spend-limit（不可重试）。
5. **排队有界、分级、公平**：无界队列 = 必然超时；交互优先、批处理可排队；多租户加权 + 老化。

来源：[Azure 配额与限流](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/quota)、[Stripe rate limiters](https://stripe.com/blog/rate-limiters)、[Redis Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)、[Anthropic 529（二手）](https://learn.microsoft.com/en-us/microsoft-cloud/dev/dev-proxy/concepts/anthropic-529-overloaded-error)。

## 3. 调研结论 B：超时、重试、熔断

1. **超时四层**：connect / first-token / chunk-idle / total；默认"全无限"是反例；用可接受误杀率与下游 p99.9 校准；deadline 绝对时间传播；下游超时 > 上游预算。
2. **重试分类**：可重试（连接、429 带 Retry-After、5xx、529、首 token 前超时）；不可重试（4xx、内容过滤、上下文超长、已 committed、spend-limit）。**committed 后不重试**（gRPC 语义）。
3. **退避必须有抖动 + 重试预算**：指数 + 上限 + ±20% jitter；gRPC retry throttling（token bucket）比无界重试可靠；重试只在一层做。
4. **放大与副作用**：多层重试可放大 243 倍；LLM 生成按 token 计费，重复重试 = 双倍账单 → 必须 requestId 去重 + 计费对账；SDK 内建重试要关闭。
5. **流式重试**：首内容前可重试/换 provider；已输出后默认失败（续写需显式开启且不适用于结构化输出）。
6. **熔断**：provider × model 粒度；失败率 + 慢调用率双阈值；最小样本；半开探测；4xx 不计入；Resilience4j 默认值可作起点。

来源：[AWS timeouts/retries/backoff](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)、[gRPC retry](https://grpc.io/docs/guides/retry/)、[Resilience4j CircuitBreaker](https://resilience4j.readme.io/docs/circuitbreaker)、[LiteLLM reliability](https://docs.litellm.ai/docs/router/learn/reliability)、[BAML timeouts](https://docs.boundaryml.com/ref/llm-client-strategies/timeouts)、[OSS metastable failures](https://www.usenix.org/conference/osdi22/presentation/huang-lexiang)。

## 4. 调研结论 C：线程模型与流式

1. **默认 MVC + 虚拟线程**（thread-per-request 规模化）：不要池化虚拟线程，用 `Semaphore` 限并发；Java 21 注意 `synchronized` 内阻塞的 pinning（JDK 24 修复），用 JFR `jdk.VirtualThreadPinned` 排查。
2. **WebFlux 只在全链路响应式时选**；在事件循环里 block 是事故。
3. **SSE 背压**：Servlet 栈无响应式背压 → 有界队列 + 快速拒绝 + 客户端断开检测；取消必须传导到上游连接（否则继续计费）。
4. **代理层陷阱**：nginx 默认 `proxy_read_timeout` 60s、buffering/gzip 会攒 SSE；SSE 端点必须关缓冲并单独设超时。
5. **bulkhead**：每 provider 独立连接池/信号量；慢 provider 不得吃光全局线程。

来源：[JEP 444](https://openjdk.org/jeps/444)、[Spring Boot task execution](https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html)、[SseEmitter javadoc](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/SseEmitter.html)、[netclaw 两阶段流式超时（工程例证）](https://github.com/netclaw-dev/netclaw/commit/7fd7593e199bb5dff4f1640c27a501fc9afaab6c)。

## 5. 调研结论 D：可观测性

1. OTel GenAI semconv 仍是 Development：**不能当稳定 ABI**；框架内部字段稳定，`gen_ai.*` 通过适配层映射并锁定版本。
2. 一次逻辑调用一个 `llm.invoke` span，重试合并为 attempt 子 span；必填 `gen_ai.operation.name`、`gen_ai.provider.name`、`error.type`；usage/token 属性按版本映射。
3. **内容默认不采集**（Opt-In），需要审计时写对象存储，日志只留引用；prompt/response 不进日志/metric。
4. 指标用低基数标签；requestId/traceId/userId/prompt 只进日志/span，不进 metric label。
5. **日志 schema**：event_name + 分组（trace/subject/llm/usage/latency/outcome/cost/content/sampling）+ 稳定枚举；金额用 Decimal 字符串 + 币种；一条日志能还原调用、重试、计费与错误。
6. SLO 覆盖可用性、TTFT、TPOT、429、结算延迟、账实差异、成本偏差；告警用多窗口燃烧率。

来源：[semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)、[client-inference](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md)、[metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)、[OTel Logs Data Model](https://opentelemetry.io/docs/specs/otel/logs/data-model/)、[SRE Workbook: alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)（抓取失败，依据公开章节/二手）。

## 6. 调研结论 E：通用计量计费

1. **五层分离**：事件→计量→计价→账单→账本/收款；计量规则与价格版本化，历史不回填。
2. 产品共性抽象：Stripe Billing Meters（meter/聚合/事件）、Metronome（contract/commit/credit/rate card）、Lago（transaction_id 去重、wallet 预付、Kafka/ClickHouse 高吞吐）、OpenMeter（Meter/Entitlement/Grant 实时额度控制）。
3. **实时准入与账务分离**：预扣（短 TTL、可回收）+ 结算（异步、可重放）+ 不可变账本 + 对账；不要把强一致账务压到实时扣减路径。
4. 幂等：事件 ID 业务确定性生成；API 幂等键（同 key 同参返回首次结果）；预扣状态机 settle/release/expire 只能终态一次。
5. 热点账户五条路线（事件异步、单行强扣、分桶、Redis 预扣、窗口批量）各有取舍；首期采用"Redis/内存预扣 + DB 持久化 reservation + 异步批量结算 + 对账"。
6. 领域对象/不变量见 01；账本不可变、余额由流水派生、finalize 后账单不可改。

来源：[Stripe usage-based](https://docs.stripe.com/billing/subscriptions/usage-based/implementation-guide)、[Stripe Meter](https://docs.stripe.com/api/billing/meter/object)、[Stripe Idempotency](https://docs.stripe.com/api/idempotent_requests)、[Metronome how-it-works](https://docs.metronome.com/guides/get-started/how-metronome-works)、[Metronome token billing](https://docs.metronome.com/guides/pricing-packaging/billing-model-guides/token-billing)、[Lago ingest](https://getlago.com/docs/guide/events/ingesting-usage)、[Lago wallets](https://getlago.com/docs/guide/wallet-and-prepaid-credits/overview)、[OpenMeter entitlement](https://openmeter.io/docs/billing/entitlements/entitlement)、[TigerBeetle two-phase](https://docs.tigerbeetle.com/coding/two-phase-transfers/)、[Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)。

### 7.2 关键发现（可直接落设计）

1. **三层命名值得借鉴**：provider deployment（一次接入/凭据/配额）≠ model group（同名部署集合）≠ 客户端别名（name）。它让"同模型多接入 + 跨模型 fallback"能共存；我们的 01 模型已补 `ProviderDeployment` 与 `ModelAlias`（见 01 §2.1）。
2. **错误分类先于重试**：LiteLLM/Portkey 都按错误类型配置策略；Spring AI 的"默认 10 次/3 分钟"是危险默认，不能照抄（我们采用 maxAttempts=2–3、只重幂等错误、指数退避+jitter、Retry-After 封顶）。
3. **流式边界最易踩坑**：一致结论是"首 chunk 前可重试/fallback，首 chunk 后不重试（除非显式续写且非结构化输出）"。我们的 04 §8 已按此设计，并记录 partial usage。
4. **熔断与并发要共享状态**：Portkey 熔断只管失败率不管并发；LiteLLM 单机错误率在多副本会漂移。我们采用 Redis 存 deployment 冷却 + 并发信号量/本地兜底（02 §5、04 §5）。
5. **预算检查与记账之间有超发窗口**：LiteLLM/Portkey 均有异步记账/预算不追溯的问题；我们采用"请求前预留 + 响应后按实际 settle"来压住并发超支（05）。
6. **usage 事实表 + 版本化价目表是共性**：request_id/attempt、route（original vs routed）、usage 按类型、cost、latency、status、estimated 标志；这直接支撑对账与争议处理。
7. **指标低基数**：把 API Key 哈希/用户 ID 做成 Prometheus label 的高基数反例应避免；我们坚持 model/provider/status/route 进 metric，key/user/request 只进 trace/log（03 §5）。
8. **观测产品在向网关补能力**：Langfuse AI Gateway（beta）与 Helicone Gateway 说明"网关+计量+观测"应同层设计；我们已把三者放在同一设计包，而不是事后拼装。
9. **产品功能与框架能力要分开**：充值/兑换码/订阅/发票/渠道运营/加价倍率/模型市场/语义路由/MCP 网关/企业 SSO 属于产品特有，首期不做（00 §3）。
10. **OpenAI 兼容作为内部统一请求模型 + providerOptions/raw passthrough**：适配成本低，又保留 provider 特有参数，避免被单一协议卡死（02 §3.2 补充）。

## 8. ADR 决策记录

| ADR | 决策 | 备选与理由 |
|---|---|---|
| ADR-001 | 模块化单体 + 明确模块边界（llm/metering），不先拆服务 | 与 atry 现状/生产蓝图一致；先立数据与契约边界，避免"拆了两次" |
| ADR-002 | MVC + 虚拟线程，流式用 SSE 桥接；不在首期引入 WebFlux | 阻塞式 provider SDK 生态成熟、调试简单；全链路响应式收益不足 |
| ADR-003 | 重试只由框架单点负责；adapter/SDK 禁止重试 | 避免重试放大/双倍计费 |
| ADR-004 | 超时四层拆分、deadline 绝对时间传播 | 避免误杀长输出/挂死；与 AWS/gRPC 实践一致 |
| ADR-005 | 计量计费采用五层模型，meter 与 price 版本化 | 通用性（token 只是单位）；历史可重算、不可篡改 |
| ADR-006 | 预扣 + 异步结算 + 不可变账本 + 对账 | 准入低延迟与账务强一致的折中；避免热点行锁压垮调用路径 |
| ADR-007 | API Key 归 identity，llm 只消费 SubjectRef | 凭证与 RBAC 同层；避免 llm 拥有身份数据 |
| ADR-008 | OTel GenAI 仅作导出契约，内部 schema 稳定 | semconv 实验态，避免版本升级破坏内部字段 |
| ADR-009 | 日志"事件名 + 分组 + 稳定枚举"，内容默认不落 | 人与 agent 可检索；安全合规 |
| ADR-010 | 首期不引入 MQ；outbox + 轮询/批量结算 + 对账 | 与 btry《Redis 降级与 MQ 边界》一致；有证据后再引入 |
| ADR-011 | 计量与额度分离（entitlement 控制面 vs invoice 账务面） | 实时准入与账单解耦；支持免费额度/套餐 |
| ADR-012 | 金额用 Decimal/整数，禁止 double；只在出账边界舍入 | 资金正确性 |

| 项 | 风险/问题 | 处理 |
|---|---|---|
| 真实 provider token 口径差异 | 同一模型不同版本 usage 字段/缓存 token 定义不同 | provider adapter 契约测试 + 对账；先接一个 provider 验证 |
| token 估算准确性 | provider 未返回 usage 时估算偏差 → 多收/少收 | 估算标记 + 对账；优先使用 provider usage；价格按估算上限预扣 |
| 多实例预扣 | 内存预扣不能跨实例 | 第二阶段迁 Redis（Lua/租户分桶）；对账兜底 |
| 结算崩溃恢复 | 内存队列丢失 | 首期 outbox/reservation 持久化 + 启动恢复；后续 MQ |
| 计费合规/发票 | 税务、发票不在本期 | 明确非目标，后续接支付/财务系统 |
| 模型弃用/价格变动 | 历史账单可重算性 | 价格版本 + 事件快照；模型别名映射 |
| 成本币种 | 上游美元、下游人民币 | 价格书按币种；汇率策略后续定义 |
| 限流公平性 | 大租户挤占 | 租户配额 + 加权队列；压测验证 |
| atry 仓库形态（D1） | 历史不干净/命名混乱 | owner 决策后一次性迁移（见 00 §7） |

## 10. 结论

调研支持本设计的三条主线：**可靠性分层（超时/重试/熔断/限流/隔离）**、**可观测优先（schema + trace + SLO + 排障）**、**计量计费五层分离（事件/计量/计价/账务/对账）**。与现有产品相比，atry 不追求功能覆盖，而追求"框架级、可复用、可验证"：provider 可插拔、策略可配置、计量与业务无关、每一步有测试与数据。
