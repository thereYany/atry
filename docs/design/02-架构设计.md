# 02 架构设计

> 本文描述模块划分、运行时组件、关键时序、并发模型、数据所有权与演进边界。实现代码不在本文范围。

## 1. 架构风格

- **模块化单体**：沿用 atry/btry 的 Maven 多模块 + Spring Modulith + ArchUnit；先在一个进程内把边界立住，未来按《生产级目标架构蓝图》拆服务。
- **模块**：`platform`、`contracts`、`identity`、`payment` 已有；新增 `llm`（调用治理）、`metering`（通用计量计费）。
- **契约先行**：`llm` 与 `metering` 只通过 `contracts` 交互；跨模块异步事件也定义在 contracts。
- **每个模块一个 starter 能力**：`llm`、`metering` 各自提供自动配置（artifact 前缀由 D1 决定，见 00 §7 D2），业务应用依赖即获得能力（与 platform starter 一致）。

## 2. 模块内部结构（约定）

```text
com.wherelee.base.modules.llm
├── api/            # 实现 contracts.llm 的入口（LlmInvoker、AdminService）
├── domain/         # 聚合/实体/值对象/领域服务/仓储接口
├── app/            # 应用服务：编排、事务边界、策略解析
├── provider/       # ProviderAdapter SPI 与实现（mock / openai-compatible / …）
├── routing/        # 路由、fallback、cooldown、健康
├── guard/          # 限流、并发舱壁、熔断、预算、超时
├── stream/         # 流式桥接、SSE 适配、取消
├── observability/  # 调用记录、日志事件、OTel 映射、指标
└── config/         # 属性绑定、自动配置
```

```text
com.wherelee.base.modules.metering
├── api/            # 实现 contracts.metering
├── domain/         # usage/meter/price/account/entitlement/invoice/recon 模型
├── app/            # 应用服务：记录用量、预扣/结算、出账、对账
├── ingest/         # 事件入口、去重、持久化、异步队列
├── rating/         # 价格解析、计价、舍入
├── account/        # 余额、预扣、流水
├── billing/        # 账期、账单、调整
├── recon/          # 对账任务与差异
└── config/
```

> 命名中**禁止**出现垂直业务词；KernelPurityTest 扫描范围覆盖 `server/*/src/main`，新模块自动纳入。

## 3. llm 运行时组件

```text
业务方
  │  contracts.llm.LlmInvocationOperations.invoke/stream
  ▼
LlmInvoker ──► RequestNormalizer ──► RouteResolver ──► PolicyResolver
  │                                     │                 │
  │                                     ▼                 ▼
  │                             ProviderRegistry    RateLimiter/Bulkhead/Circuit/Quota
  │                                     │
  │                                     ▼
  │                            AttemptExecutor ──► ProviderAdapter SPI ──► 上游
  │                                     │  ▲
  │                                     ▼  │ 重试/fallback/冷却
  │                            StreamBridge / UsageExtractor
  │                                     │
  ▼                                     ▼
Outbox(调用记录 + usage 事件)  ◄── InvocationRecorder ── LlmObservability
```

### 3.1 组件职责

| 组件 | 职责 | 关键不变量 |
|---|---|---|
| `LlmInvoker` | 对外入口；生成 requestId；串联预扣、执行、结算 | 同一 requestId 幂等 |
| `RequestNormalizer` | 统一请求模型、参数校验、预算/租户注水 | 不修改业务语义 |
| `RouteResolver` | 按 taskType/租户/成本/延迟选候选链 | 候选为空快速失败 |
| `PolicyResolver` | 合并全局/租户/provider/model 四级策略 | 策略越具体优先级越高 |
| `ProviderRegistry` | provider 厂商定义、协议能力、adapter 工厂 | 不持有具体接入凭证（由 DeploymentRegistry 管理） |
| `DeploymentRegistry` | deployment（接入）注册、模型映射、配额/健康 | 同 provider 多 deployment 独立配额/冷却 |
| `ModelResolver` | 客户端 alias → model group → 候选 deployment | 记录 original model 与 routed model（fallback 归因） |
| `ProviderAdapter`（SPI） | 协议适配：请求转换、调用、流式解析、usage 提取、错误映射 | 只依赖 domain 模型，不依赖 Spring Web |
| `AttemptExecutor` | 单次尝试：超时、取消、错误分类、指标 | committed 后不再重试 |
| `Router/Cooldown` | 失败 provider 冷却、fallback 链推进 | 冷却到期自动恢复，不主动探测 |
| `Guard` 组件族 | 多维限流、并发舱壁、熔断、预算 | Redis 故障时本地兜底，不全局 429 |
| `UsageExtractor` | provider usage 解析/估算，标记来源 | 估算必须 `source=ESTIMATED` |
| `StreamBridge` | 上游流→客户端 SSE；首 token/空闲超时；断连取消 | 内容不缓存、不重放已输出段 |
| `InvocationRecorder` | 调用记录 + usage outbox（本地事务） | 记录失败不影响调用结果，但必须告警 |
| `LlmObservability` | 结构化日志、span、指标、采样 | 内容默认不落；字段 schema 稳定 |

### 3.1.1 内部统一请求模型

采用 **OpenAI Chat/Completions 兼容的内部统一模型**作为框架内部协议（`LlmRequest`/`LlmResponse`），并保留 `providerOptions` 透传与 `raw` 扩展位：

- 优点：provider 适配成本最低；mock/OpenAI 兼容 provider（DeepSeek 等）几乎零转换；测试可用统一 fixtures。
- 约束：provider 特有能力（tools/thinking/cache 控制等）走 `providerOptions`，不污染通用字段；adapter 负责映射与校验。

### 3.1.2 过滤器/顾问链（可选扩展）

借鉴 Spring AI Advisor 链的"栈式"语义，框架内部提供 `LlmFilter` 链（order 越小越先请求、越后响应）：

- 内置：计量 filter（预扣/结算）、观测 filter（日志/trace/metric）、内容脱敏 filter、预算 guard；
- 可扩展：业务自定义 filter（提示词模板、RAG 上下文注入、安全策略）；
- 约束：filter 只能修改请求/响应元数据，不得绕过重试/计费主链路；链的异常语义与切面顺序在 03 中定义。

### 3.2 ProviderAdapter SPI（语义）

| 方法 | 输入 | 输出 | 约束 |
|---|---|---|---|
| `capabilities()` | — | 支持的 operation/stream/tools | 用于路由 |
| `invoke(req, deadline)` | 统一请求 + 截止时间 | 统一响应 + usage | 阻塞式；超时由外层控制 |
| `stream(req, sink, deadline)` | 统一请求 + 流回调 | 完成/异常 | 首 token、chunk、finish、usage 回调；取消通过 sink/线程中断 |
| `providerOptions()` | — | 支持的扩展参数 schema | 供上层校验/透传，不改变统一模型 |
| `mapError(throwable)` | 原始异常 | `LlmError`（category/retryable/billable/providerCode） | 统一分类，禁止 adapter 自行重试 |
| `estimateUsage(req)` | 请求 | usage 估算（可选） | 用于预扣与缺失 usage 兜底 |

> 设计约束：**adapter 不做重试/不做计费**；重试由 `AttemptExecutor` 全局唯一负责，避免"SDK 重试 + 框架重试"叠加。

## 4. 关键时序

### 4.1 非流式调用（预付费）

```text
Client → LlmInvoker
 1. 认证/主体解析（identity API Key，缓存）
 2. 生成/校验 requestId（幂等）
 3. 估算 token 上限 → metering.reserve（短事务/内存预扣）
 4. RouteResolver + PolicyResolver
 5. AttemptExecutor → ProviderAdapter.invoke（带 deadline）
 6. 解析 usage（真实/估算）→ 计算金额（metering.rate? 或随 settle）
 7. 本地事务：写 t_llm_call_record + outbox(LlmCallCompleted, usage)
 8. metering.settle（异步消费 outbox；失败重试/对账）
 9. 返回结果 + usage + requestId + route 信息
```

失败路径：错误分类 → 重试/fallback/终止；终止时 `release` 预扣（或 `settle` 部分用量，若已产生 token）。失败是否计费由策略与 `billable` 决定。

### 4.2 流式调用（SSE）

```text
Client(SSE) → LlmInvoker.stream
 1-4 同上（reserve 按 max_tokens 估算）
 5. ProviderAdapter.stream：
    - 首 token 到达前失败：按重试策略换 attempt/候选
    - 首 token 到达后：进入 committed，不再重试
    - chunk → StreamBridge → SseEmitter（flush、背压、客户端断开检测）
    - chunk 间空闲超时 / 总时长兜底
    - 正常结束：拿到 usage（stream_options include_usage 或估算）
    - 中断：记录已输出 token 估算，partial usage
 6. 结算：同非流式；中断按已产生用量结算
 7. 客户端断开：取消上游连接（避免继续计费），按已产生用量结算
```

### 4.3 预扣/结算/释放

- **reserve**：按 `max_tokens` 和价格上限估算金额，写入 Reservation（PENDING，短 TTL），同时内存预扣防并发超卖。
- **settle**：实际 usage 计价后，从预扣转正式扣减（部分结算），生成 ledger；`settle + release = reserved`。
- **release**：调用失败/未产生用量时释放；超时由 `ReservationExpiryJob` 回收。
- 并发：同一 reservation 用状态 CAS（PENDING → SETTLED/RELEASED/EXPIRED），只允许一次终态。

## 5. 并发与线程模型

| 场景 | 模型 | 理由/约束 |
|---|---|---|
| HTTP 请求（非流式） | MVC + 虚拟线程（Boot 4 `spring.threads.virtual.enabled`） | 阻塞式 provider SDK 可安全使用；不要池化虚拟线程，用信号量限并发 |
| 流式 SSE | MVC `SseEmitter`/`ResponseBodyEmitter` + 虚拟线程处理 provider 阻塞流 | 避免 WebFlux 全链路依赖；背压靠有界队列 + 快速断开 |
| 上游并发隔离 | 每个 provider/model 独立 `Semaphore`（bulkhead） | 一个慢 provider 不拖垮全局；并发上限按配额计算 |
| 限流 | 本地令牌桶 + Redis Lua 分布式令牌桶；`maxInFlight` 用信号量 | 维护每维度（租户/provider/model）配额；Redis 故障本地兜底 |
| 异步结算 | 单写者/分片 worker + 有界队列 + 批量事务 | 避免热点账户行锁；批量大小/间隔可配 |
| 定时任务 | 单实例 `@Scheduled` 起步，生产用分布式调度（后续） | 多实例需锁/分片；对账/回收任务必须可重入 |

### 5.1 容量与默认值（待压测校准）

| 参数 | 初始默认 | 说明 |
|---|---|---|
| 每 provider 最大在途 | `min(配额, 计算值)`；计算值 ≈ QPS × p99 / 0.7 | 超限快速拒绝/排队 |
| 有界队列长度 | ≤ 2 × 在途上限 | 无界队列 = 必然超时 |
| DB 连接池 | 按工作线程数 × 事务占比估算，不超过 MySQL 连接上限的 60% | 避免连接池成为隐藏队列 |
| 结算批大小 | 100–500 事件/批；间隔 10–50ms | 可观测队列深度，积压告警 |
| SSE 超时 | 首 token 30–60s；chunk 空闲 60s；总时长按 max_tokens 估算 | 按真实分布 p99.9 校准 |

### 5.2 背压与过载

- 入口：`maxInFlight` 信号量 + 有界队列 + 快速失败（429/503 + Retry-After）。
- 上游：SSE 写入阻塞时停止读上游（TCP 背压）；客户端断开立即取消上游。
- 结算：队列深度超阈值时降级（丢弃可重算的聚合、保留原始事件）、告警、限流准入。
- 降级顺序：模型档位降级 → 缓存/模板回复 → 直接 429/503；绝不无界排队。

## 6. 数据所有权与事务边界

| 模块 | 拥有的表 | 事务边界 |
|---|---|---|
| `llm` | `t_llm_call_record`（调用记录，脱敏）、`t_llm_outbox`（调用完成事件） | 调用结束后一个本地事务写记录+outbox；不与上游网络调用同事务 |
| `metering` | `t_metering_usage_event`、`t_metering_meter`、`t_metering_price_book/rate_card`、`t_metering_account`、`t_metering_ledger`、`t_metering_reservation`、`t_metering_invoice*`、`t_metering_recon*` | 预扣/结算各自短事务；账本与账户同事务；出账批量事务 |
| `identity` | `t_user`、`t_user_role`、`t_api_key` | 已有约定 |
| `payment` | 已有支付表 | 已有约定 |

- **禁止跨模块直连表**（数据边界门禁会扫描）；跨模块只通过 contracts/事件。
- LLM 调用不占用数据库事务（网络调用期间无 DB 事务），完成后落记录/outbox，避免"长事务 + 网络"。
- outbox 派发（LlmCallCompleted → metering 记用量）至少一次；metering 按 eventId 幂等。

## 7. 配置模型

```yaml
atry:
  llm:
    providers:
      mock:
        type: mock
        capabilities: [chat, embedding]
        limits: { rpm: 100000, tpm: 100000000, maxInFlight: 2000 }
      deepseek:
        type: openai-compatible
        base-url: https://api.deepseek.com
        credential-ref: env:DEEPSEEK_API_KEY   # 只存引用
        limits: { rpm: 600, tpm: 200000, maxInFlight: 64 }
    routes:
      default:
        candidates:
          - { provider: deepseek, model: deepseek-chat, weight: 100 }
        fallback: [ { provider: mock, model: mock-small } ]
    policies:
      default:
        timeout: { connect: 5s, first-token: 45s, chunk-idle: 60s, total: 10m }
        retry: { max-attempts: 3, initial-backoff: 300ms, max-backoff: 2s, jitter: 0.2, budget: 0.1 }
        circuit: { failure-rate: 0.5, slow-call-rate: 0.6, min-calls: 20, open-wait: 30s, half-open-probes: 5 }
        rate-limit: { rpm: 600, tpm: 200000, max-in-flight: 64 }
    metering:
      async-settlement: true
      flush-interval-ms: 20
      batch-size: 200
  metering:
    price-books:
      default:
        currency: CNY
        rates:
          - meter: llm.tokens
            model: mock-small
            input-per-1k: "0.001"
            output-per-1k: "0.002"
```

- 凭证只允许 `env:`/`kms:` 引用；配置打印时脱敏。
- 策略支持四级覆盖：全局 → 租户 → provider → model；解析顺序固定并可在日志中看到命中的策略版本。

## 8. 部署与演进

- 首期：单进程模块化单体；`btry-app` 示例宿主 + mock provider 用于集成测试/演示。
- 中期（有真实负载证据后）：`llm` 与 `metering` 可按契约拆为独立服务；拆之前必须先有 outbox/事件与数据所有权。
- 网关接入（APISIX）与 WAF/TLS 属于部署层，不在本期模块实现。
- 观测：Micrometer + OTel（已有），GenAI semconv 映射集中在 `llm.observability` 适配层。

## 9. 扩展点

| 扩展点 | SPI/接口 | 用途 |
|---|---|---|
| Provider | `ProviderAdapter` | 新增模型厂商（OpenAI 兼容、Anthropic、本地推理） |
| 路由 | `RouteResolver`/策略 | 按任务/成本/延迟/租户路由 |
| 计量 | `MeterDefinition` 配置 + `UsageExtractor` | 新增计量维度（token、请求数、GPU 秒） |
| 计价 | `RatingEngine`/价格书 | 阶梯价、套餐、模型差价、促销 |
| 额度 | `EntitlementPolicy` | 免费额度、试用包、周期重置 |
| 观测 | `LlmLogSink`/OTel exporter | 日志/指标导出后端 |
| 存储 | repository 接口 | 从 MySQL 到分析库/时序库的迁移 |

## 10. 关键取舍（详见 07 ADR）

1. MVC + 虚拟线程，而不是 WebFlux：阻塞式 SDK 生态成熟、调试简单；流式用 SSE 桥接即可。
2. 重试只在框架单点做，adapter/SDK 禁止重试：避免重试放大（见 04）。
3. 调用记录 + outbox 落库后再异步结算：调用路径不为账务付出同步 DB 成本；崩溃由 outbox/对账兜底。
4. 预扣在内存 + 短 TTL 持久化：准入低延迟，账务强一致由后续结算与对账保证。
5. 计量规则/价格版本化、历史不回填：演进安全，避免"改规则把历史账单改了"。
