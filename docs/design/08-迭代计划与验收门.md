## P0：骨架与契约（不写业务逻辑）

**目标**：模块、契约、迁移、门禁、mock provider 可运行；后续阶段在稳定骨架上迭代。

| 交付 | 内容 |
|---|---|
| 模块骨架 | `llm`、`metering` 子模块 + starter/自动配置（artifact 前缀随 D1）；`contracts` 增加 `llm`/`metering` 包 |
| 门禁 | ArchUnit 新增规则、Modulith `allowedDependencies`、表清单基线、KernelPurity 扫描、数据边界 |
| 契约 | `LlmInvocationOperations`、`MeteringOperations`、`ApiKeyOperations` 的接口/DTO/事件（空实现可编译） |
| 数据 | Flyway 迁移（`t_llm_*`、`t_metering_*` 首批表）；种子数据（mock provider/价格/账户） |
| mock provider | 可配置延迟/错误/token/流中断，供测试与压测 |
| 文档 | 本设计包评审通过；README/架构图更新 |

**验收**：`mvn test` 全绿（含门禁）；模块图无环；空实现调用返回明确"未实现"而非 NPE；一条 mock 调用端到端可跑通并产生 `llm.call.started/finished` 日志（字段占位）。

## P1：调用框架最小闭环（无治理）

**目标**：业务可通过 `contracts.llm` 发起 mock 调用，拿到统一响应/usage；有调用记录与基础日志。

| 交付 | 内容 |
|---|---|
| 调用链 | `LlmInvoker` → `ProviderRegistry` → `MockProvider` → 统一响应/usage |
| 数据 | `t_llm_call_record` + outbox（调用完成事件） |
| 日志 | `llm.call.started/finished/failed` 基础字段（trace/subject/llm/usage/latency/outcome） |
| 测试 | 单元 + 集成 + 日志 schema 基础校验 |

**验收**：mock 调用端到端成功/失败各 1 条；日志可按 requestId 还原；无敏感内容；调用记录/outbox 落库。

## P2：可靠性治理

**目标**：限流、超时、重试、熔断、隔离、fallback 按设计生效，并有故障注入证据。

| 交付 | 内容 |
|---|---|
| 策略 | `PolicyResolver` 四级覆盖；配置校验 |
| 超时 | 四层超时 + deadline 传播；流式两阶段 |
| 重试 | 分类 + 退避/抖动 + retry budget；committed 语义 |
| 熔断/隔离 | provider×model 熔断、bulkhead、本地+Redis 限流 |
| fallback | 候选链、冷却、降级可见 |
| 证据 | 06 §5 故障矩阵执行结果；重试放大/重复计费为 0；过载压测报告 |

**验收**：故障矩阵全部通过并留存记录；压测：mock 非流式 ≥ 1,000 req/s（或达到阶段目标）、p99 达标；出错不雪崩；Redis 故障本地兜底生效。

## P3：可观测与 AOP 完整化

**目标**：注解/AOP、结构化日志、trace、指标、SLO 看板全部可用；"一条日志定位"成立。

| 交付 | 内容 |
|---|---|
| 注解 | `@LlmCall`/`@LlmStream`/`@UsageMetered`/`@BudgetGuard`/`@Sensitive` + 切面顺序测试 |
| schema | 全部事件 JSON Schema + 测试；采样/脱敏规则 |
| trace | OTel GenAI 映射层 + span 树断言 |
| metrics | 03 §5 指标落地；SLO 规则/看板（Prometheus/Grafana 可选） |
| 证据 | 一条 requestId 的端到端 trace + 日志 + 指标截图/文本；agent 查询脚本 |

**验收**：日志/指标/trace 字段验收清单全部勾选；脱敏测试通过；切面性能开销 p99 < 15ms。

## P4：通用计量计费（预付费闭环）

**目标**：从调用事件到余额扣减/账本/账单/对账的完整链路（mock 充值）。

| 交付 | 内容 |
|---|---|
| 事件与计量 | 事件入库、去重、meter 聚合 |
| 计价 | 价格书/费率卡版本化；rating |
| 账户 | 预扣/结算/释放；账本；余额 |
| 出账 | 账单/明细/状态机（可先日/月账单） |
| 对账 | L1–L5 校验；差异表与处理 |
| 测试 | 不变量/并发/故障注入；与 llm 联动 |
| 压测 | 事件注入 → 结算吞吐/延迟、账户热点、对账耗时；与基线对照 |

**验收**：10 万事件对账差异=0；重复投递/并发 settle 不重不漏；余额/账本/账单可重算；结算崩溃恢复通过。

## P5：真实 provider、成本与产品化边界

**目标**：接 1 个真实 provider（DeepSeek 或等价），验证真实 usage/延迟/错误；形成展示与面试证据。

| 交付 | 内容 |
|---|---|
| 真实适配 | `OpenAiCompatibleProvider`（base-url/鉴权/流式/usage），契约测试通过 |
| 成本 | 真实价格书；成本归因/预算；估算 vs 实际对账 |
| 流式 | 真实 SSE 端到端；TTFT/TPOT 指标 |
| 证据 | 压测报告（mock + 真实）、故障演练、对账报告、演示页/README |
| 复盘 | ADR 更新、遗留问题清单 |

**验收**：真实 provider 小流量跑通；成本与 provider 账单一致（容差内）；TTFT/错误率有基线；演示可一键复现。

## 阶段依赖与顺序理由

```text
P-1（决策/环境）
  └─► P0（骨架/契约/门禁）
        ├─► P1（最小调用闭环）
        │     └─► P2（可靠性治理）
        │           └─► P3（可观测/AOP 完整化）
        └─► P4（计量计费）——可与 P2/P3 并行，但依赖 P0 契约与 P1 事件
                                └─► P5（真实 provider/成本/证据）
```

- 先 P1/P2 再 P3：可靠性产生大量日志/指标需求，P3 才能设计出真正需要的字段。
- 计量计费（P4）与可靠性可并行，但必须先有 P1 的调用完成事件；否则计量没有输入。
- P5 最后：真实 provider 用于校准 mock 假设与性能目标，不阻塞框架设计。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 范围膨胀（做成 SaaS/前端/多 provider） | 严格按非目标清单评审；每阶段只做本阶段验收项 |
| 过度设计影响交付 | 每阶段有最小可用版本；优化必须有基线/对照数据 |
| 真实 provider 不稳定/无 key | mock 先行；真实 provider 作为校准项，不阻塞 |
| 计量一致性难 | 不变量测试 + 对账 + 故障注入；先单实例再扩展 |
| 性能数据不可信 | 固定环境/脚本/版本；记录原始输出；多轮取中位数 |
| 设计文档与实现漂移 | 实现阶段每个 PR 更新 ADR/设计差异记录 |
