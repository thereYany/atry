# 04 可靠性设计

> 目标：在"上游不可控、流量不确定、成本按量"的前提下，保证调用不雪崩、不放大、不重复计费、可降级、可恢复。设计依据见 07 调研（AWS/gRPC/Stripe/Resilience4j/Azure/LiteLLM 等）。

## 1. 五条原则

1. **单点重试**：重试只由框架 `AttemptExecutor` 负责；SDK/adapter/provider client 的重试必须关闭，避免乘法放大（5 层 × 3 次 = 243 倍的真实事故模式）。
2. **有界优先**：所有队列、并发、重试、等待都有上限；无界队列只是把超时变成必然。
3. **先分类再动作**：每个错误先归入稳定 taxonomy（03 §6），再决定重试/降级/终止/计费。
4. **预算思维**：时间预算（deadline）、重试预算（token bucket）、成本预算（budget guard）三者联动；预算耗尽立即失败，不硬撑。
5. **committed 语义**：收到响应头/首 token 后视为已提交——不重试、不无缝续写、按已产生用量结算。

## 2. 超时：四层拆分

| 超时 | 覆盖阶段 | 非流式 | 流式 | 默认起点 |
|---|---|---|---|---|
| connect | DNS + TCP + TLS 建连 | 必设 | 必设 | 5s |
| timeToFirstToken | 请求已发送到首个内容/响应头 | 等价于总超时 | **必设**（覆盖排队/推理） | 30–45s，按 provider p99.9 |
| chunkIdle | 两个 chunk 之间最大停顿 | 不适用 | **必设**（抓流挂死） | 30–60s |
| requestTotal | 墙钟上限（兜底） | 必设（按 max_tokens 估算） | 只做兜底（长输出可能很久） | 10min（可配） |

规则：

- **两阶段流式超时**：首 token 前用 `timeToFirstToken`；首 token 到达后切换为 `chunkIdle` watchdog；`requestTotal` 始终兜底。
- **deadline 传播**：入口按 `min(全局上限, 租户/任务上限)` 计算 absolute deadline，逐层传递；下游超时 > 上游剩余预算，禁止逆序。
- **超时是绝对时间**（`deadline = now + budget`），不是每跳重新计时；重试消耗同一预算。
- 超时值用"可接受误杀率 + 下游分位"确定（如 p99.9 + 网络 padding），不用拍脑袋；上线后用真实分布校准。
- 代理层陷阱：nginx `proxy_read_timeout`（常见默认 60s，以部署版本为准）、`proxy_buffering`/gzip 会攒住 SSE；SSE 端点必须关闭缓冲并单独设置超时（部署清单，不在代码内）。
- Java 侧：不在事件循环里阻塞；虚拟线程下注意 `synchronized` 内阻塞导致 pinning（Java 21），用 JFR `jdk.VirtualThreadPinned` 排查。

## 3. 重试

### 3.1 可重试判定（由错误分类给出，不靠字符串）

| 可重试 | 条件 |
|---|---|
| 是 | 建连失败/TLS 失败、429 且 Retry-After 允许、500/502/503/504、529 overloaded、首 token 前读超时、未收到任何响应头 |
| 条件式 | 429 配额耗尽（`quota_exhausted`）→ 不重试；`stream_interrupted` 仅首内容前可重试 |
| 否 | 400/401/403/404/413/422、content_filter、context_too_long、spend-limit、**已 committed（已输出内容）** |

### 3.2 退避与预算

```text
delay(n) = min(maxBackoff, initialBackoff * multiplier^(n-1)) * (1 ± jitterRatio)
默认：initial=300ms, multiplier=2, max=2s, jitter=±20%, maxAttempts=3（含首次）
```

- **重试预算（retry budget）**：按 provider 维护 token bucket（如容量 10、每次失败 -1、每次成功 +0.1），低于阈值时暂停重试直接失败/降级。gRPC 的 retry throttling 是成熟实现，优先采用这一模式而非无限重试。
- **Retry-After 优先**：429 响应带 `retry-after`/`retry-after-ms` 时按服务端指示等待；不按自己的退避硬撞。
- **重试放大防护**：重试与并发舱壁/限流联动，重试流量计入配额；重试链最多跨 2 个候选，禁止深链。
- **幂等**：重试必须携带同一 requestId；上游支持幂等键时透传；计费按 requestId 去重（见 05）。
- **流式**：首内容前失败 → 同组重试/换 provider，调用方只看到一个流；已输出后失败 → 默认失败（记录部分用量），不自动续写；tool_call/JSON 结构化输出绝不续写。

## 4. 熔断（Circuit Breaker）

- 粒度：**provider × model**（同 provider 不同模型独立）；状态 CLOSED/OPEN/HALF_OPEN。
- 阈值：失败率（如 50%）+ **慢调用率**（如 60%，能抢在下游真崩前降载）双阈值；最小样本数（如 20）避免小流量误开；OPEN 等待 30–60s；HALF_OPEN 只放行少量探测（如 5 个），成功则关闭。
- 4xx（参数/鉴权/内容）不计入失败率；只统计 5xx/超时/连接失败/overloaded。
- `CallNotPermitted` 快速失败（不占线程、不排队），直接进入 fallback/降级。
- 与路由联动：OPEN 的候选从路由链跳过；冷却（cooldown）到期自动恢复，不做高频主动探测（可用低频小请求探测，失败只降权不摘除）。
- 实现：优先复用已有 Resilience4j（btry 已依赖 resilience4j-spring-boot3/micrometer），策略通过配置生成，避免自研状态机。

## 5. 限流与并发控制

### 5.1 多维限流

| 维度 | 作用 | 实现 |
|---|---|---|
| RPM（请求/分钟） | 防止短时高频 | 令牌桶（容量=突发≤2s 量，速率=配额 80–90%） |
| TPM（token/分钟，输入+输出） | 长上下文真实瓶颈 | 按估算/实际 token 令牌桶；请求前按 max_tokens 预占，结束后按实际补差 |
| 最大在途（in-flight） | 防线程/连接/显存打爆 | `Semaphore`，按 provider/model/租户 |
| 日配额/预算 | 成本控制 | 计数器 + 预算 guard（402/降级） |
| 租户公平 | 防单租户挤占 | 租户级配额 + 加权轮询/优先级队列 |

### 5.2 算法取舍

| 算法 | 优点 | 代价 | 用途 |
|---|---|---|---|
| 令牌桶/GCRA | O(1)、允许可控突发 | 参数需调 | 入口 RPM/TPM |
| 滑动窗口日志（ZSET+Lua） | 任意 60s 精确 | O(N) 内存 | 对精度敏感、低频高价值 |
| 漏桶 | 严格平滑 | 突发被压 | 保护固定吞吐下游 |
| 信号量 | 直接限并发 | 不解决速率 | in-flight |

- 实现基线：本地 Caffeine/令牌桶 + Redis Lua 分布式；脚本原子、短小、`EVALSHA`；key 全部走 KEYS；用 Redis `TIME` 避免多实例时钟漂移。
- **Redis 故障**：本地令牌桶按实例均分配额兜底，记录 `infra.redis.fallback` 指标；限流器不得 fail-closed 打挂全站（与 btry《Redis 降级与 MQ 边界》一致）。
- 429 回执：返回 `Retry-After` + 明确的 `error_type=rate_limited`/`quota_exhausted`，让调用方区分"退避重试"与"停止/充值"。

### 5.3 排队与优先级

- 有界队列（长度 ≤ 2×在途），排队等待计入 deadline；超时快速拒绝。
- 分级：交互式（客服）> 后台批处理（离线/embedding）；多租户加权 + 老化防饥饿。
- 过载时**先拒绝可重试的低优先级流量**，不要在队列里堆到全部超时。

## 6. 隔离、线程模型与背压

- HTTP：MVC + 虚拟线程（`spring.threads.virtual.enabled=true`）；流式用 `SseEmitter`/`ResponseBodyEmitter`，不引入 WebFlux 全链路（避免 R2DBC/响应式 SDK 的生态成本）。
- 虚拟线程：不要池化；并发限制用 `Semaphore`；`ThreadLocal` 中只放小对象；排除 pinning。
- **Bulkhead**：每个 provider/model 独立信号量 + 独立 HTTP 连接池/超时；一个慢 provider 不能吃光全部线程和连接。
- **背压**：Servlet 栈没有响应式背压——入口有界队列 + 快速拒绝；SSE 写入阻塞时停止读上游（TCP 自然背压）；客户端断开必须传播取消到上游连接，避免"客户端走了还在生成/计费"。
- 长连接资源：SSE 连接数有上限（按实例内存/文件描述符），超限快速 503；空闲超时清理。

## 7. 路由、降级与故障转移

- 路由输入：taskType、租户、model hint、预算、历史健康/延迟/成本。
- 候选链：主 provider（权重）→ 同模型备用部署 → 跨模型（强→弱）→ 静态降级回复；fallback 深度上限（如 2），禁止无限套娃。
- 健康：被动统计为主（错误率/延迟窗口），低频小请求主动探测为辅；探测失败降权不摘除。
- 降级分级并**对调用方可见**（响应头/字段 `degraded=true`）：
  1. 模型档位降级（强→弱）；
  2. 参数降级（降低 max_tokens、关闭推理/工具）；
  3. 缓存/模板回复；
  4. 明确失败（429/503 + Retry-After）。
- 成本/延迟路由：按任务打标分池；预算到量后降级而非直接中断业务。

## 8. 流式调用专项

| 场景 | 处理 | 计费 |
|---|---|---|
| 首 token 前失败 | 同组重试/换 provider；调用方无感 | 不计费 |
| 已输出部分内容后上游断 | 终止流，标记 `stream_interrupted`；不自动续写（除显式开启续写且非结构化输出） | 按已产生 token 结算 |
| 客户端断开 | 取消上游连接；记录 `cancelled` | 按已产生 token 结算 |
| chunk 空闲超时 | 中断、结算、告警 | 按已产生 token |
| 代理缓冲/超时 | 关闭 gzip/buffering；SSE 专用超时；部署文档固化 | — |
| 流式 usage 缺失 | 用 tokenizer 估算或按已输出 chunk 计数，`source=ESTIMATED` | 估算值结算，标记可对账 |

## 9. 默认参数（首期，压测/线上校准）

| 参数 | 默认 | 校准方法 |
|---|---|---|
| connect timeout | 5s | 网络基线 p99.9 + padding |
| first-token timeout | 45s | provider p99.9 + 排队预算 |
| chunk idle | 60s | 真实流分布 |
| request total | 10min | max_tokens 估算 + 实测 |
| max attempts | 3（含首次） | 错误率/重试放大指标 |
| backoff | 300ms→2s，×2，±20% | 429 恢复时间分布 |
| retry budget | 容量 10，成功 +0.1，失败 -1 | 重试放大与成功率 |
| circuit failure rate | 50%，min 20 calls，open 30s | 故障注入 |
| slow call rate | 60%（阈值 p99×1.5） | 延迟分布 |
| per-provider in-flight | min(配额, QPS×p99/0.7) | 压测 |
| rate limit 使用率 | 配额 80–90% | 429 比例 |

### 9.1 容量估算示例（Little's Law）

- 目标 QPS=1000、上游 p99=200ms、目标利用率 70%：
  `in-flight ≈ 1000 × 0.2 / 0.7 ≈ 286`；单实例取 300，集群按实例数均分但保留 20% 余量。
- provider 配额 RPM=600：令牌桶速率约 9–10 req/s、突发 ≤ 2s 量（约 20），多实例共享 Redis 计数。
- SSE 并发=500、平均流时长 30s → 在途流 ≈ 500；需校验 FD/内存/转换器线程池上限。
- 以上公式只做初始配置，必须用压测校准（06 §6）。

## 10. 反模式清单（评审必查）

1. 客户端超时 < 排队时间 → 全量超时 + 重试雪崩。
2. SDK 内建重试 + 框架重试叠加。
3. 已输出内容后重试/续写 → 重复文本 + 双倍计费。
4. 无界队列/无限重试/无预算。
5. 限流器 fail-closed 强依赖 Redis。
6. 熔断计入 4xx、无最小样本、无半开探测。
7. 一个慢 provider 共享全局线程池/连接池。
8. SSE 被代理缓冲/被默认 60s 超时截断。
9. 客户端断连未取消上游 → 继续计费。
10. 只记录最终错误，不记录 attempt/耗时分解 → 无法归因。
11. 照搬框架危险默认：如 Spring AI 默认 `spring.ai.retry` 10 次/初始 2s/×5/上限 3min，且 OpenAI SDK 自身 `max-retries=3`，叠加后尝试次数更高；重试必须按错误类型与预算显式配置，并关闭 SDK 内建重试。
12. 熔断/并发状态只存在单机：多副本下错误率漂移、并发失控；共享状态用 Redis（deployment 冷却/信号量）+ 本地兜底。

## 11. 验收与故障注入（详见 06）

- 429（带/不带 Retry-After）、建连超时、首 token 超时、chunk 空闲超时、5xx、529、流中断、客户端断开、Redis 故障、DB 故障、结算 Worker 崩溃。
- 每个场景断言：不重试放大、不重复计费、指标/日志字段正确、最终状态可对账。
- 压测矩阵：稳态/尖峰/过载/长尾/慢 provider 隔离；输出 p50/p95/p99、错误率、429 比例、重试率、结算积压。
